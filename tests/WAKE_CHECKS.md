# Wake acoustic regression and processing cost

The wake-only grammar can decode unrelated speech as **Hey Sally** even with word confidence 1.0. It now proposes candidates only. A second decoder using the existing model's full vocabulary must confirm each finalized candidate as an exact Hey Sally before it can activate the assistant. Ordinary results do not run full decoding. The verifier is created lazily and reset between candidates; both decoders share the same model.

The detector keeps at most ten seconds in memory and rejects oversized segments rather than verifying a truncated tail. It can hold one finalized Hey result until the next endpoint, so a native silence boundary between Hey and Sally does not discard half the phrase. It then verifies the combined audio. Completed/rejected segments and close erase the buffer. After a blank endpoint, only its last second remains as onset context for speech beginning at that boundary; older audio is erased. No tail of an overflowing segment is retained. Each native endpoint fully finalizes its feature state; verification never inherits earlier decoded speech. No recordings or transcripts are saved. Long continuous speech without an endpoint can therefore require a pause before an intentional wake. Capture remains continuous while verification runs; this changes neither the spoken wake phrase nor the command recognizer.

`check-playlists.ps1` includes `WakeDetectorCheck.java`: on-demand creation, exact/rejected results, current-segment replay, a wake split across endpoints, overflow, recovery and cleanup. The optional `check-wake.py` compiles the actual WakeDetector, VoskWakeDecoder and WakePhrase classes with `WakeAcousticCheck.java`, then replays native Vosk using the application's downloaded model. It covers the production decoding pipeline, not Android microphone/callback behavior. It also checks long silence, repeated wakes and varied pauses on one live detector.

Run from the repository root. The optional acoustic check needs Python 3, a JDK supporting Java 17, a local synthetic/public mono PCM16 16-kHz WAV corpus, matching official desktop Vosk Java/native runtimes, JNA and Gson. It downloads nothing and accesses neither the phone nor microphone. Put generated audio, runtimes and reports under ignored `.tools/`, outside release assets.

On Windows, generate synthetic speech using installed local voices:

```powershell
powershell.exe -NoProfile -File ./tests/generate-wake-corpus.ps1
python -X utf8 ./tests/check-wake.py --corpus .tools/wake-acoustic/corpus/synthetic-corpus.json --library <path-to-libvosk.dll> --vosk-jar <path-to-vosk-0.3.45.jar> --jna-jar <path-to-jna-5.18.1.jar> --gson-jar <path-to-gson-2.13.2.jar> --report .tools/wake-acoustic/result.json
```

Keep the native library's companion DLLs in its folder. The verified Windows runtime was the official PyPI `vosk-0.3.45-py3-none-win_amd64.whl`, SHA-256 `6994ddc68556c7e5730c3b6f6bad13320e3519b13ce3ed2aa25a86724e7c10ac`; extract its `vosk/*.dll` files. Use the matching official Maven Vosk 0.3.45 Java jar, SHA-256 `9e38e96e4448a41d889bb254b2f8424945554945c6e77e1cd97a3d8633fac2ba`. The Python package need not be installed. Android still uses Vosk 0.3.75: desktop results are qualified accordingly. JNA/Gson versions remain the app's existing versions; no product dependency was added.

The 10 October synthetic corpus used Microsoft David Desktop and Microsoft Zira Desktop: 42 unrelated utterances and four intentional wakes at normal/slower rate. It includes subject, administration and they, ordinary sentences, and confusing phrases such as they said/they sell it. The unverified wake-only grammar produced five false wakes. Continuous full decoding and the on-demand pipeline both rejected all 42 unrelated samples and recognized all four intentional wakes. These observations establish a regression for this corpus, not a general false-wake rate or Android result. Reports store sample numbers, outcomes and timing, not decoded transcripts.

Desktop processing cost fell with on-demand verification, but battery claims require phone measurements. During a private Pixel trial, continuous full decoding averaged about 32.5% of one CPU core over 75 seconds. The listener was active and not microphone-silenced, but the user reported no response to repeated intentional wakes. That variant therefore failed device validation despite preliminary absence of false beeps. The on-demand variant must still pass intentional/background speech trials before it is usable. The published APK remains unchanged.

Repeat video-call/background speech at normal volume, intentional Hey Sally at the user's normal distance/accent with screen locked/off, and extended unplugged listening. Check actual ready beeps and diagnostic events; native desktop recognition does not prove audible behavior. USB charging permits CPU-counter comparisons but cannot establish battery drain. Low-power system hotword hardware is not used; continuous microphone capture still has a battery cost. A genuine Hey Sally played by a speaker can activate the app because no speaker verification is implemented.
